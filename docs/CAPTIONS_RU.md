# Автоописание датасета

Модель по умолчанию — Qwen/Qwen2.5-VL-3B-Instruct; API проверяет доступ и закрепляет точную HF-ревизию перед заданием. В этой правке модель не заменена и её ограничения не отключены. Отказ модели считается неудачным описанием, а не caption. Качество распознавания и чувствительные материалы требуют проверки на реальной GPU и собственных примерах.

## Как использовать

1. Создайте персонажа и задайте trigger. Все подписи должны использовать его одинаково.
2. Загрузите изображения или нарежьте исходное видео на подходящие клипы/кадры.
3. В настройках датасета задайте дополнительные правила captions: какие видимые переменные признаки описывать. Не требуйте выдумывать скрытые детали.
4. Запустите «Описать фотографии». Проверьте предупреждения у файлов и исправьте неверные детали. Изменение текста вручную снимает предупреждение этого описания.
5. Только после проверки создавайте новое обучение. Уже запущенная задача использует неизменяемый snapshot, изменение редактора её не меняет.

Для Krea/Klein используйте изображения. Для Wan описывайте короткие клипы с действиями. Автоописание видео анализирует восемь хронологических выборочных кадров, а не всё видео; движение между ними может быть пропущено. Нарезка остаётся отдельным существующим действием FFmpeg и сохраняет группу исходного видео.

## Контракт результата

Модель получает инструкцию вернуть JSON с `caption`, `person_visible`, `face_visible`. Флаги принимают boolean/null; неизвестная видимость не превращается в отрицательную. Генерация детерминированная (`do_sample=False`), лимит 320 новых токенов. Выполняется максимум две попытки на материал.

Постобработка убирает обёртку markdown, `Caption:`, внешние кавычки и повторные префиксы trigger; приложение добавляет trigger один раз. Неправильный JSON, неверные типы/противоречивые флаги, пустые, чрезмерно длинные, оборванные подписи и типичные ответы-отказы не сохраняются как подпись. После двух неудач старый caption остаётся, причина появляется у файла и в логе, задача помечается как требующая проверки. Это проверка формата, не автоматическое доказательство фактической точности или личности человека. Все автоматические подписи сохраняют отметку необходимости просмотра.

## Развёртывание исправления

1. Разверните backend/frontend из этой ветки в Timeweb.
2. Запустите GitHub Actions → **Build GPU agent** на этой же ветке. Дождитесь успешной сборки. Не арендуйте GPU ради проверки сборки.
3. Задайте `AGENT_IMAGE=ghcr.io/crystalcali/maymaystudio-gpu:<полный SHA успешной сборки>` в Timeweb. Сам Git push не обновляет работающий GPU-контейнер.
4. На существующем агенте дождитесь завершения активных задач и сохранения результатов. Затем замените контейнер новой командой Studio, сохраняя его рабочий том. Сервер YouGPU пересоздавать не нужно. Если в томе сохранён `worker.json`, агент использует существующую регистрацию; иначе получите свежий одноразовый код.
5. Сначала опишите небольшой тестовый набор: фото с лицом, фото без человека и короткий клип. Проверьте подписи и предупреждения, затем используйте большой датасет.

Исправлена и первая регистрация: агент больше не отправляет пустой `Authorization: Bearer ` до получения worker token. Авторизация heartbeat, заданий и загрузки результатов сохранена.

CPU-тесты проверяют контракт, повторную попытку, сохранность старого caption, границы датасетов и реальный HTTP-путь регистрации. Они не подтверждают GPU-качество описаний или сборку Docker.
