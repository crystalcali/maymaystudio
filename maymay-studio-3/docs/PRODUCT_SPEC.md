# MayMay Studio v3 — техническое задание глобального обновления

Это целевое ТЗ. Реализованный объём и отложенные функции первой сборки перечислены в README.md; они не объявляются выполненными только на основании этого документа.

Статус: проект ТЗ с зафиксированными решениями пользователя по инфраструктуре; не реализованное приложение. Проверка документации и уточнение требований: 27 октября 2026 года.

## 1. Продукт и основной результат

Постоянная личная студия создания фото и видео, доступная с телефона, планшета и компьютера. Основной персонаж — May; другие персонажи создаются независимо. Пользователь работает с персонажами, сценами, референсами и результатами. Выбор тренера, файлов VAE, команд, совместимых версий и форматов выполняет система.

Приложение разворачивается в Timeweb Cloud App Platform — выбор подтверждён пользователем. Выбор и аренда мощностей YouGPU доступны непосредственно в web app уже в первом релизе. Отсутствие или смена GPU не отключает интерфейс, галерею, редактор датасетов и историю. Это переработка архитектуры, а не дальнейшее расширение notebook-приложения.

Обязательные сценарии: обучить персонажа на Krea или Klein и сразу проверить; генерировать на существующей LoRA без обучения; применить несколько совместимых LoRA; оживить выбранное фото; обучить Wan-адаптер отдельно от image-LoRA; продолжить обучение после перезапуска вычислительного узла.

## 2. Основание и ограничения анализа

Учтены доступная переписка, предоставленные логи и ранее сформулированные требования v2. Полное чтение соседних чатов через инструмент контекста сейчас недоступно. Файл «Вставленный Markdown.md» найден по известному идентификатору, но сервис не вернул читаемый текст; его содержимое не использовано. Аудит текущего исходного кода и проверка конкретной тестовой генерации из другого чата здесь не выполнялись.

Проблемы из обсуждения и требования, которые из них следуют:

| Наблюдение | Требование к v3 |
|---|---|
| Неверные адреса и переезды файлов HF, 401/403/404 | Реестр компонентов, ревизии, проверка доступа до запуска GPU, понятная диагностика |
| Конфликт torch из venv и torchvision из системного Python | Изолированные воспроизводимые образы, без наследования случайных system-site-packages |
| RAW и Turbo, trainer weights и Diffusers folders путались | Отдельные типизированные рецепты и проверенная загрузка результата обучения |
| 20 GB диск Kaggle не вмещал RAW | Раздельные постоянное хранилище и GPU-кэш, проверка диска до аренды |
| Выгрузка в CPU замедляла работу; encoder на CPU оставлял GPU простаивать | Измерение этапов, профиль под реальное оборудование, CPU offload только при необходимости |
| В галерею попадали JSON, кэш и веса | Галерея из реестра медиа-артефактов, не из обхода файловой системы |
| Один триггер May был зашит в код | Независимые персонажи, датасеты, триггеры, LoRA и версии |
| Сохранялась LoRA без полного состояния | Раздельные экспорт адаптера и checkpoint для resume |
| Preview не позволял своевременно оценить сходство | Регулярные фиксированные тестовые сцены и сравнение сохранений |
| Режимы памяти и две GPU не означали реального ускорения | Статус поддержки на конкретном сочетании recipe/hardware, без обещаний по одному наличию переключателя |

Loss не считается оценкой сходства May; его рост на нескольких десятках шагов не доказывает ни провал, ни успех обучения. Решение принимается по тестовым изображениям и устойчивости обучения.

## 3. Проверенные возможности инфраструктуры

Timeweb Cloud App Platform разворачивает код из репозитория, поддерживает Next.js, Python/FastAPI и контейнерные способы деплоя. Контейнер приложения заменяется при redeploy, поэтому пользовательские данные и база должны находиться вне него. Предлагаемая конфигурация: Next.js/React + FastAPI, внешняя PostgreSQL и S3-совместимое хранилище. Это проектное решение, а не требование купить конкретный тариф.

YouGPU документирует REST API управления каталогом, инстансами, шаблонами, SSH-ключами, балансом и хранилищем. API находится в активном развитии, поэтому интеграция изолируется в provider adapter с контрактными тестами. Секрет API передаётся сервером через X-API-KEY, не браузером пользователя.

JupyterLab в документации — шаблон инстанса с параллельным SSH-доступом. Отдельный арендный продукт «kernel» не подтверждён: интерфейс студии различает способ подключения к вычислителю и тип тарифицируемого ресурса.

Критично: STOPPED у YouGPU продолжает тарифицироваться. Для освобождения ресурсов и прекращения аренды нужен terminate. Диски оплачиваются отдельно. Удаление инстанса уничтожает его системный диск. Автоматическое завершение аренды разрешено только для созданных студией узлов, после подтверждённого сохранения нужных файлов и при включённой пользователем политике.

Облачный диск YouGPU подключается при создании, а не к уже работающему инстансу; документация указывает 5–100 GB. Этого нельзя автоматически считать достаточным для всех весов Wan, двух экспертов и нескольких версий. Каноническое хранение студии — S3; локальный GPU-диск и диск YouGPU служат кэшем/рабочим хранилищем с явным учётом ёмкости.

## 4. Архитектура

Компоненты:

1. Web UI на Timeweb: студия, персонажи, датасеты, галерея, обучение, мощности, задачи, помощь.
2. API: авторизация, рецепты, артефакты, управление заданиями, YouGPU adapter.
3. PostgreSQL: источник истины о задачах, попытках, версиях, аренде и артефактах. Долгая задача не выполняется внутри HTTP-запроса.
4. Диспетчер: выдаёт задания, проверяет heartbeat, срок аренды задачи и права исполнителя; после перезапуска сверяет состояние с БД и provider.
5. GPU agent: исполняет только поддерживаемые версии рецептов, сообщает этапы/метрики, загружает результаты. Предпочтительно исходящее HTTPS-соединение к студии, без обязательного публичного порта GPU.
6. S3: оригиналы, версии датасетов, LoRA, checkpoints, медиа, параметры и миниатюры. Большие файлы передаются через multipart/presigned URL непосредственно между клиентом/worker и S3.

Для MVP достаточно одной PostgreSQL и отдельного процесса диспетчера; Redis добавляется при подтверждённой необходимости. Новое развёртывание web app не должно прерывать выполняющийся GPU job.

Подключение worker: одноразовый pairing-код → регистрация → проверка GPU/драйвера/RAM/диска/связи с S3 → проверка recipe image → состояние Ready. Provider API key не передаётся worker; ему выдаются отдельный короткоживущий токен и минимальные права на файлы конкретного задания.

## 5. Менеджер мощностей

Два обязательных режима:

- Подключить существующий узел: SSH bootstrap либо одна ячейка в Jupyter, запускающая агент. Notebook нужен для первоначального подключения, а не для постоянного интерфейса студии. Если среда запрещает фоновую работу, это отображается как ограничение.
- Создать узел YouGPU из студии: каталог предложений, GPU/VRAM/RAM/диск, доступность, актуальная цена, образ, накопитель, бюджет и политика завершения аренды.

В карточке: состояние аренды и агента раздельно; GPU и использование VRAM; RAM; рабочий и постоянный диск; очередь; загруженная модель; доступные recipes; стоимость по действующему предложению; время аренды; оценка накопленного расхода; ссылка SSH/Jupyter при наличии.

Действия: подключить, проверить, назначить, запретить новые задачи и дождаться текущей, остановить процессы, завершить аренду, отключить от студии. «Остановить задачу», «выгрузить модель», «остановить инстанс» и «завершить аренду» — разные операции.

Политики: ручной выбор GPU по умолчанию; автоматический подбор — только в установленных границах цены, бюджета и количества узлов. ETA и стоимость появляются после замеров; отдельно учитываются загрузка весов, установка, прогрев, вычисление, выгрузка и оплачиваемый простой. При потере агента новый платный узел не создаётся автоматически без сверки с провайдером.

### Выбор мощности под конкретную задачу

Основной маршрут первого релиза: пользователь задаёт обучение или генерацию → система отбирает совместимые предложения → пользователь выбирает вариант непосредственно в web app → студия создаёт и подключает инстанс. Подключение существующего инстанса остаётся дополнительным сценарием. Управляемая аренда не откладывается на последующий релиз; позже добавляются автономное масштабирование и автоматическая смена ресурсов.

Вместо длинного каталога по умолчанию показывать до трёх вариантов: «Сбалансированный», «Минимальная стоимость задачи», «Самый быстрый». Варианты рассчитываются среди доступных совместимых предложений и могут совпадать; не создавать искусственные различия. Остальные предложения открываются через «Все мощности».

Главные сведения карточки:

- GPU, число карт и VRAM на каждой; подходящий рецепт и ограничения памяти.
- Актуальная цена за час в валюте провайдера; возраст цены/доступности и повторная проверка перед арендой.
- Ожидаемая скорость: секунд на шаг обучения либо время одного фото/видеоролика при выбранных настройках.
- Ожидаемое время и полная стоимость именно текущего задания, диапазон и степень уверенности.
- Разделение времени подготовки и вычисления, наличие кэша и дополнительная стоимость диска/хранения/передачи, если применима.

Почасовая цена — основной ориентир пользователя. Конкретный числовой потолок бюджета пока не задан; не подставлять выдуманный лимит. В интерфейсе предусмотреть максимальную цену за час, лимит расходов сессии и предупреждения. Более дешёвая GPU за час не считается автоматически более дешёвой для завершения задачи.

Оценщик использует версионированные замеры для сочетания recipe, GPU, числа GPU, dtype/quantization, offload, разрешения, batch, attention backend и наличия кэша. Для видео дополнительно учитываются кадры, эксперты и VAE decode; для генерации — steps, CFG и адаптеры. Нельзя переносить скорость одной карты на другую только по объёму VRAM либо считать ускорение DDP равным числу карт.

До первого замера показывать предварительный диапазон из сопоставимых тестов с пометкой об источнике; при отсутствии пригодных данных — «Скорость пока не измерена». Платная калибровка не запускается скрытно: пользователь видит её как этап задачи. Во время работы ETA пересчитывается по устойчивой скорости после прогрева, отдельно от затрат на скачивание и установку. История содержит оценку до запуска и фактический результат для дальнейшей калибровки.

Расчёт полной оценки: почасовой тариф × ожидаемое оплачиваемое время аренды + применимые дополнительные расходы провайдера. Время включает подготовку, вычисление, preview, сохранение и ожидаемый простой; правила округления/резервирования берутся из актуального тарифа. Вычислительное время может оцениваться по оставшимся optimizer steps и измеренной скорости, но не заменяет собой полное время аренды. Постоянные расходы студии и S3 показываются отдельно. Не обещать гарантированную стоимость по предварительной оценке.

Пункты «обучить + генерировать» и «только генерировать» используют один генератор. После обучения добавляется шаг проверки и публикации выбранной версии LoRA в карточке персонажа; дублирующихся меню для одного двигателя нет.

На основном экране: персонаж May по умолчанию, фото/видео, описание сцены, референсы, формат кадра, количество вариантов, стиль/LoRA с ползунком, кнопка создания. Steps/CFG/precision/trainer paths скрыты в расширенном режиме. Возможность редактирования технических настроек сохраняется через «Эксперт», собственные профили и импорт рецепта.

Визуальный стиль: светлый минимализм, стекло и мягкие акценты Frutiger Aero, аккуратная типографика, крупные сенсорные элементы и адаптация к узкому экрану. Основной сценарий: выбрать персонажа → описать сцену → создать варианты → сравнить → редактировать или отправить фото в Wan I2V. Интерфейс показывает причину недоступности операции и способ её исправить.

Выбор пресета заполняет совместимые компоненты и параметры. Доступны «Восстановить preset», собственное имя и собственные пути/репозитории; пользовательские изменения отмечаются и проходят ту же проверку. Импорт LoRA: файл, Hugging Face или Civitai; система определяет архитектуру и формат, проверяет доступ и предлагает необходимые trigger words. Несколько адаптеров имеют независимые веса; ускоряющая LoRA — отдельный тип с собственным расписанием шагов. Не заявлять поддержку произвольной LoRA по одному совпадению расширения safetensors.

Каждый recipe фиксирует код и commit, digest образа, зависимости, ревизии весов и хэши, формат входов/LoRA, поддерживаемые GPU, параметры и их границы, правила offload и sampling, тестовые примеры, дату проверки источника. Ссылки на main используются для исследования, но не как незаметно обновляющаяся production-зависимость.

Статусы recipe: изучен по документации → проходит минимальный GPU smoke test → проверено обучение/генерация → рекомендован. Последний статус присваивается только после полного end-to-end прогона с оценкой результата. Опубликованная команда сама по себе не означает готовый pipeline.

## 7. Актуальные рецепты и исходные параметры

Источники собраны 27.10.2026. Ниже отдельно указаны опубликованные ориентиры и предложенные эксперименты для May. Они не заменяют GPU-приёмку. Параметры принадлежат конкретному backend: похожие названия флагов не означают одинаковую семантику.

### Krea 2: LoRA

Основной маршрут по рекомендациям авторов: RAW-train → Turbo-infer. Musubi-компоненты: RAW DiT, Qwen-Image VAE и Qwen3-VL-4B-Instruct. Не подменять энкодер обычным Qwen3. В исходном рецепте Musubi: rank/alpha 32/32, AdamW8bit, LR 1e-4, gradient checkpointing, SDPA, timestep shift 2.5, без дополнительного weighting. Латенты и текст кэшируются до тренировки.

Для May предложить два экспериментальных профиля: осторожный rank16/LR5e-5 и исходный rank32/LR1e-4. Размер по умолчанию 1024 с buckets на достаточно мощной GPU; 768 — отдельный экономичный профиль. Количество предъявлений и шагов рассчитывать по объёму датасета и эффективному batch, а не зашивать 1200 для всех наборов. Первые сравнения сохранять через 200 шагов; итоговую длительность выбирать по фиксированным тестам. Фигура, лицо, родинка и пропорции головы — отдельные пункты визуальной приёмки.

### Krea 2: генерация и preview

Turbo: опубликованный режим 8 шагов, CFG отключён, mu 1.15. В официальном CLI CFG-off выражается cfg=0; в Musubi руководство использует guidance_scale=1. UI хранит смысл «без CFG», а адаптер выставляет правильный флаг. Для RAW у авторов есть пример 52 шага/CFG3.5, тогда как Musubi показывает свой пример 28/5.5; не смешивать эти расписания в одном универсальном preset.

Обучение с block swap несовместимо с Musubi preview через turbo_dit. Решение v3: отдельный preview worker на свободной GPU или RAW-preview с правильным CFG. При единственном узле — последовательное переключение с честной оценкой затрат. Тренировочные thumbnails не объявлять проверкой идентичности.

### Klein 9B: LoRA

Тренировать Base9B, model_version=klein-base-9b; компоненты: соответствующий DiT, FLUX.2 AE, Qwen3 8B со всеми shards. Репозиторий AE в актуальном коде BFL — FLUX.2-dev; имена и существование файлов сверять по реальному дереву, не копировать устаревшую строку документации.

Ориентир Musubi: BF16 на поддерживающей GPU, rank32, AdamW8bit/LR1e-4, flux2_shift и weighting none, gradient checkpointing. Rank16/LR5e-5 — собственный экономичный эксперимент. FP8 только по совместимой схеме; не считать любой готовый FP8 checkpoint подходящим для trainer.

Первичная приёмка LoRA — на Base9B. Применение на distilled 9B — отдельный тест и отдельная запись совместимости, а не автоматическое обещание переноса по аналогии с Krea.

### Klein 9B: генерация / редактирование

Base: опубликованный ориентир 50 шагов и guidance4 при 1024. Distilled: 4 шага/guidance1. Редактирование использует референсные изображения; не называть это SDXL img2img со strength, если выбранный pipeline так не работает. Пользователь выбирает «Создать фото» или «Изменить по референсу», а UI показывает только действующие параметры. Отдельно фиксируется формат каждой внешней LoRA.

### Wan 2.2 A14B: LoRA

Отдельные recipes для T2V и I2V. Два эксперта high/low; UMT5-XXL и VAE семейства Wan2.1 для A14B. VAE от 5B несовместим. Для I2V кэширование учитывает исходный кадр (--i2v). Один или два последовательных запуска экспертов выбирает система; пользователю доступны понятные профили, детали экспертности скрыты.

Диапазоны Musubi: I2V low 0–900, high 900–1000; T2V low 0–875, high 875–1000; preserve_distribution_shape. Опубликованный пример rank32/LR2e-4/shift3.0 — пример тренера, не доказанный оптимум персонажа A14B. Для May начать сравнительный эксперимент rank16–32/LR5e-5–1e-4. Фото и клипы — разные профили нагрузки; клипы сначала 17 или 33 кадра, число кадров 4n+1, затем расширение после замера памяти. Это наша программа проверки, не официальный гарантированный рецепт.

### Wan 2.2: генерация

A14B T2V и I2V загружают правильные пары экспертов. Исходный ориентир inference flow shift: T2V12, I2V5; не переносить его механически в обучение. Точный scheduler, число шагов и guidance закрепляются за версией backend и обычным либо ускоренным checkpoint. Для первого собственного quality smoke test: короткий ролик, 81 кадр при 16 FPS, 480p-профиль, 30–50 шагов и guidance3.5–5 как диапазон сравнения; это не обещание production-качества и не единый preset для 5B/A14B. FPS экспорта нельзя путать с временной моделью генератора.

TI2V5B — отдельная архитектура с собственным VAE и допустимыми размерами, взятыми из кода. Для неё нельзя просто переиспользовать ограничения A14B. LoRA A14B не считается подходящей для 5B. В первом релизе обучение 5B не предлагается.

Конкретный ориентир официального TI2V5B-кода: Wan2.2 VAE, 1280×704 либо 704×1280, 121 кадр, 24 FPS, 50 шагов, shift5, guidance5. Это исходный полноценный режим, не обещание скорости на любой GPU. Сокращённый тестовый режим и загрузка внешних 5B-LoRA требуют самостоятельной приёмки. Базовым Wan14B в v3 считаем Wan2.2 A14B; если нужен прежний Wan2.1 14B, он добавляется отдельным recipe с собственными весами и совместимостью.

### Подбор под оборудование

A100/H100 и другие совместимые GPU получают BF16-профили по итогам тестов; T4 — отдельный FP16/low-memory режим, а не основная целевая платформа. При достаточной памяти сначала тестировать без block swap и CPU text encoder. Offload включается по потребности. Multi-GPU DDP ускоряет обработку батчей, но не объединяет VRAM; model/tensor parallel training — отдельная функция после однокарточной приёмки. Заявленные требования VRAM подтверждаются замером полной цепочки, включая encoder, VAE, LoRA и preview.

## 8. Подсказки и защита от неверной настройки

У каждой настройки есть: что изменяет, влияние на качество/время/память, допустимый диапазон для текущего recipe, исходный источник и предложенное значение. Примеры:

- «Эта модель работает без CFG: negative prompt не используется».
- «Выбран Base9B: режим качества — 50 шагов; ускоренный distilled — другой checkpoint».
- «Референс задаёт внешность, prompt описывает движение».
- «Увеличение кадров повышает память; FPS экспорта не ускоряет физическое движение модели».
- «Вес LoRA — сила её влияния; высокая величина может ухудшить сцену и детали».
- «Сохранить адаптер — для генерации. Сохранить состояние — для продолжения обучения».
- «Две GPU изменяют эффективный batch. Одинаковое число шагов не означает одинаковый объём обучения».
- «Остановка инстанса YouGPU не прекращает аренду».

Negative prompt показывается и применяется только при реальной поддержке выбранным backend/режимом. Для Krea RAW он доступен при CFG; Turbo показывает пояснение об отключённом CFG. Для Klein не отождествлять embedded guidance с CFG/negative prompt. Для Wan настройка зависит от обычного либо ускоренного рецепта и обеих стадий denoising. FAQ включает быстрый старт по каждому двигателю, выбор GPU, импорт LoRA, checkpoints/resume, подготовку видео и расшифровку типичных ошибок 403/404/OOM/несовместимости.

До аренды проверяются существование компонентов, права доступа и расчёт требуемого места. На worker до вычисления проверяются хэши и полнота файлов, все shards, библиотечные импорты, CUDA, совместимость dtype, GPU/RAM/диск и запись в S3. Проверка, требующая GPU, учитывается как оплачиваемый этап. Переход к квантованию не меняет качество незаметно: пользователь видит выбранный профиль. Для моделей и внешних LoRA показываются источник, лицензия, статус принятия условий и совместимость.

## 9. Датасеты, персонажи и галерея

Карточка персонажа содержит эталоны, триггер, версии наборов, LoRA по архитектурам, выбранные версии и тестовые результаты. May сохраняет приоритет исходных эталонов. Анатомическую сторону родинки необходимо подтвердить по оригиналам и записать в карточку; в этом ТЗ сторона не определена из-за отсутствия самих эталонов. Асимметрия глаз и расположение родинки не должны искажаться зеркальными аугментациями. Другие персонажи не используют общий жёстко заданный trigger.

Редактор: фото/ZIP/видео; VLM captions; сцены/кадры/клипы/overlap; дубликаты; видимость человека и лица; ручное исправление; принятие/исключение; версии. Автоматический captioner не считается доказательством правильной личности. Sparse frame captioning явно отличается от анализа движения полноценного клипа.

Train/validation разделяются по исходным видео, сериям и связям дубликатов до перемешивания. Перекрывающиеся клипы не расходятся между выборками. Обучение получает неизменяемый snapshot с manifest/hash. Фотодатасет учит внешности, а клипы добавляют временные признаки; не обещать обучение походке из фотографий.

Галерея хранит фото/видео, миниатюры, seed, prompt, модели, адаптеры, recipe и их версии, источник и историю преобразований. Можно сравнить, выбрать варианты, отправить в edit/I2V, скачать, включить в датасет через ручной отбор. LoRA, checkpoints и служебные файлы находятся в отдельных представлениях.

Предпочтения May для тестовых сцен: естественные бытовые и сложные композиции, читаемое окружение без постоянного размытия, разнообразие эмоций и освещения, правдоподобные пропорции головы и тела. Съёмка в стиле телефона — выбираемый творческий профиль: допускаются тени, умеренный шум, небольшая смазанность; он не должен закрепляться во всех обучающих примерах.

## 10. Очередь, память и сохранение

Состояния задач: queued → preparing → downloading → caching → loading → running → checkpointing/preview → uploading → succeeded. Дополнительно cancelling, cancelled, failed, connection_lost, reconciling, paused_at_checkpoint. Фактическая пауза заявляется только при поддержке тренером; иначе это остановка после сохранения с последующим resume.

У задачи отдельные попытки исполнения. Heartbeat/lease и идемпотентные команды предотвращают двойной запуск и повторную платную аренду при сетевых сбоях. Закрытие браузера не отменяет работу. Готовый файл становится артефактом после проверки и подтверждения загрузки; временные и недописанные файлы не видны как результат.

Из очереди можно удалить ещё не запущенное задание. Выполняющееся сначала отменяется с ожиданием завершения процессов; удаление карточки истории не считается отменой. Прогресс и ETA показываются по этапам скачивания, кэширования, обучения, preview, генерации, кодирования и загрузки. При отсутствии измерений отображается «Оценка появится после первых шагов», а не выдуманное время.

Checkpoint включает адаптер, optimizer/scheduler/scaler/RNG, step и позицию данных насколько поддерживает тренер, world size, batch, версии recipe/model/dataset. Возможность resume проверяется реальным прерыванием и восстановлением, с оговоркой о недетерминизме. Существующая v1 LoRA без state импортируется как начальные веса, не выдаётся за точный resume.

Короткая серия генераций может использовать прогретый model worker. По смене модели/профиля — контролируемая выгрузка или пересоздание процесса с проверкой VRAM. Долгая тренировка исполняется изолированно; один и тот же GPU не получает конкурирующие тяжёлые задания без явно проверенного режима. Перевод на CPU не является универсальным способом избежать OOM.

## 11. Порядок реализации и приёмка

1. Интеграционный прототип: проверить реальный YouGPU аккаунт, API, SSH/Jupyter, создание/подключение агента, обмен с S3 и завершение аренды. Уточнить ограничения Timeweb по процессам/соединениям. Результат — рабочий контракт инфраструктуры.
2. Постоянная основа: Timeweb deploy, БД/S3, авторизация, импорт текущих материалов и LoRA, менеджер подключённых узлов, журнал расходов.
3. Один вертикальный сценарий Krea: реальное обучение → checkpoint/preview → resume → Turbo с несколькими LoRA → медиа в постоянной галерее. Однокарточный GPU, затем оптимизация. Пока он не прошёл, массовое добавление двигателей не считается прогрессом готовности.
4. Klein Base train + generate/edit, отдельная проверка distilled, пользовательские адаптеры.
5. Wan I2V как основной видеосценарий, затем T2V, затем A14B character LoRA по фото и клипам. 5B остаётся генерационным вариантом.
6. Редактор датасетов, автоматические captions и сравнение checkpoints, мобильная доводка, FAQ и экспорт/резервное копирование.
7. Автономное управление арендой и масштабированием, расширенная калибровка оценок, прогрев; multi-GPU после измерений и тестов отказов. Выбор предложения, создание инстанса из web app и базовый контроль расходов входят в этапы 1–3.

Этап 6 частично разрабатывается параллельно с основой, но не заменяет приёмку вычислительных сценариев. Сроки и бюджет разработки оцениваются после выбора режима деплоя и интеграционного прототипа.

Критерии готовности: web redeploy и закрытие браузера не теряют задачи/медиа; отмена действительно освобождает GPU-процессы; данные не пропадают при terminate узла; повтор callback не создаёт дубликат результата; потеря сети не создаёт второй узел; несовместимая LoRA отклоняется до генерации; все заявленные pipelines проходят GPU тест на закреплённых образах; May визуально сравнивается с эталонами на новых сценах; токены отсутствуют в frontend/логах; расходы различают GPU, хранение и простой.

MVP: один владелец с авторизацией, один/несколько подключаемых узлов, ручной выбор ресурса; основная приёмка на одной подходящей мощной GPU. Публичная многопользовательская SaaS, совместное редактирование, оптимизированный distributed training и обучение Wan5B — за пределами первого релиза. Z-Image/Pony можно сохранить как legacy-адаптеры, но их перенос не блокирует Krea/Klein/Wan.

## 12. Зафиксированные решения и оставшиеся допущения

1. Подтверждено: Timeweb App Platform.
2. Подтверждено: выбор и аренда мощностей из web app. Основной экран показывает необходимое для выбора, оценки скорости, времени и стоимости обучения/генерации.
3. Подтверждён почасовой ориентир цены. Сумма в час пока не указана; возможность настроить лимит входит в интерфейс.
4. Рабочее допущение: личная студия с авторизацией, несколько персонажей, без публичной общей галереи. Оно не блокирует проработку инфраструктуры.
